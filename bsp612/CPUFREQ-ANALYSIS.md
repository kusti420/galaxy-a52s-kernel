# qcom-cpufreq-hw crash on 6.12: analysis (2026-11-14)

Runs analysed: ab-s60, ab-s61, ab-s62 (phone 2, kexec from the 6.18 harness), plus the earlier
live-insmod deadlock. Offline work only: code, DT and logs. Nothing was run on a phone.

## Verdict

The cpufreq driver is not the culprit, and neither is the voltage. **The 6.12 kernel boots without
`android_arch_task_struct_size=512`.** Loading cpufreq lets WALT (`sched-walt.ko`) finish its
initialisation for the first time. WALT then writes its 456-byte per-task struct just past the end
of every `task_struct`, which is the start of the next `task_struct` in the slab. That zeroes the
neighbour task's `thread_info` (flags, ttbr0, preempt_count, scs_sp, cpu), `__state`, `stack`,
`usage` and `flags`, for every task in the system, inside a `stop_machine()`.

Every symptom in the three logs follows from that layout. The evidence is below.

Ranking:

| # | Cause | Likelihood |
|---|-------|-----------|
| 1 | Missing `android_arch_task_struct_size=512`. The WALT vendor data overruns into the next task_struct. cpufreq is only the trigger. | **Proven from code and layout; matches every symptom** |
| 2 | kexec drops all of Qualcomm's DT `bootargs` (cause of #1, and also loses `cpufreq.default_governor=performance` and others) | Certain (mechanism of #1) |
| 3 | Driver gaps vs 5.4: no SDPM CX/MX frequency writes on 6.12 | Real difference, but cannot cause this crash |
| 4 | Undervolt or EPSS misprogramming | Ruled out (see below) |
| 5 | kCFI or struct-layout mismatch in the cpufreq module, or the LMh irq handler | No evidence. The driver's own code has run for milliseconds only. |

## 1. The mechanism, step by step

1. **The kernel is built with dynamic task_struct vendor data.**
   `bsp612/out/gki/.config:978-979`: `CONFIG_GKI_DYNAMIC_TASK_STRUCT_SIZE=y`,
   `CONFIG_GKI_TASK_STRUCT_VENDOR_SIZE_MAX=1280`.
   `bsp612/kernel/include/linux/sched/task.h:244-250`: `android_task_vendor_data(p)` returns `p + 1`,
   the first byte after `struct task_struct`.
   `bsp612/kernel/init/main.c:916-937`: `arch_task_struct_size = sizeof(struct task_struct)` unless the
   boot parameter `android_arch_task_struct_size=<n>` adds `n` bytes.
   `bsp612/kernel/kernel/fork.c:1049-1050`: the `task_struct` slab is created with `arch_task_struct_size`.
   Without the parameter, `p + 1` is **outside** the object.

2. **Qualcomm sets that parameter, but only in the DT.**
   `bsp612/devicetree/qcom/yupik.dtsi:33` (and `lahaina.dtsi:34`): `bootargs = "... android_arch_task_struct_size=512 ..."`.
   Our kexec dtb carries it too (`fdtget out-ack/kx/android-r02.dtb /chosen bootargs`).
   But `kexec_file_load` replaces `/chosen/bootargs` with the kexec command line
   (`ack/drivers/of/kexec.c:556-562`). The 6.12 kernel's printed command line in all three runs has no
   `android_arch_task_struct_size` (`grep -c` = 0 in each `prev-console.txt`). Our command line is
   `drivers612/androidboot/out/android-cmdline.txt` (generated by
   `drivers612/androidboot/pack-android-612.sh:194-198`) plus the GKI built-in `CONFIG_CMDLINE`
   (`out/gki/.config:580`, extend mode). Neither has the parameter.

3. **The layout overlaps exactly.** pahole on `bsp612/out/gki/vmlinux` (the running build, 6.12.81-4k-g8a69376da734):
   `sizeof(struct task_struct) = 5184 = 81 x 64`, so with 64-byte slab alignment `p + 1` is the
   first byte of the next object. pahole on `out/dist/.../sched-walt.ko`:
   `sizeof(struct walt_task_struct) = 456` (fits in 512). The overlay:

   | offset | neighbour task_struct field | WALT field written by `init_new_task_load()` | effect seen |
   |---|---|---|---|
   | 0 | `thread_info.flags` | `wts->flags` | TIF flags lost |
   | 8 | `thread_info.ttbr0` (SW PAN) | `mark_start = 0` | user accesses use a zero TTBR0, so uaccess faults on user addresses (s62: "Unable to handle kernel paging request at 000000558713b262", Oops with `pc 0000007fa9c8c920` in busybox) |
   | 16 | `thread_info.preempt_count` | `window_start = 0` | preempt_count 0, then underflow: "BUG: scheduling while atomic: swapper/0/0/0xfffffff7" (s61); printk shows "C0" (`in_task()` false) for a task |
   | 24 / 32 | `scs_base` / `scs_sp` | `sum`/`demand`, `coloc_demand`/`sum_history[0]` | shadow call stack pointer garbage: return addresses come from junk, so the kernel pc ends up at user-looking addresses |
   | 40 | `thread_info.cpu` | `sum_history[1]` (= 0 at init) | **"CPU: 0" printed by migration/1,2,5,6,7 at the same microsecond.** On this kernel `raw_smp_processor_id()` is `current_thread_info()->cpu` (`bsp612/kernel/arch/arm64/include/asm/smp.h:32`) |
   | 40 vs `td->cpu` | - | - | `kernel BUG at kernel/smpboot.c:137` = `BUG_ON(td->cpu != smp_processor_id())` (`bsp612/kernel/kernel/smpboot.c:137`) |
   | 56 | `stack` | `sum_history_util[0..3] = 0` | task stack pointer NULL |
   | 64 | `usage` | `sum_history_util[4]` + hole | refcount trashed |
   | 68 | `flags` (PF_KTHREAD) | `curr_window_cpu[0..]` memset 0 | **"WARNING at kernel/kthread.c:76"** = `WARN_ON(!(k->flags & PF_KTHREAD))` in `to_kthread()` (`bsp612/kernel/kernel/kthread.c:74-78`), from `kthread_should_stop/park` |

   (task_struct offsets: `pahole -C task_struct bsp612/out/gki/vmlinux`; WALT offsets:
   `pahole -C walt_task_struct .../kernel/sched/walt/sched-walt.ko`.)

4. **Why it appears exactly when cpufreq registers, on all CPUs at once, in the stopper threads.**
   - WALT does nothing at module load. `walt_module_init()` (`soc-repo/kernel/sched/walt/walt.c:6229-6239`)
     only hooks `android_vh_update_topology_flags_workfn`, or schedules `walt_init` if
     `topology_update_done` is already set.
   - That hook fires from `drivers/base/arch_topology.c:286-291`. Its work is queued by
     `init_cpu_capacity_callback()` (`:453-478`), a `CPUFREQ_CREATE_POLICY` notifier, only after
     **every CPU has a cpufreq policy**: right after "EM: created perf domain" for cpu7.
   - `walt_init()` (`walt.c:6154-6218`) runs. It needs a policy per cluster (`walt.c:3495-3501`,
     `WALT_PANIC(!policy)`), registers all WALT scheduler hooks (`register_walt_hooks()`), then
     `stop_machine(walt_init_stop_handler)` (`walt.c:6199`). The handler calls `init_new_task_load()`
     on **every process/thread and every idle task** (`walt.c:6089-6117`, writes at `walt.c:3031-3081`).
   - Every corrupted thread in s60 and s61 is a `migration/N` stopper thread ("Comm: migration/0..7",
     "Stopper: 0x0 <- 0x0"). These are the threads that ran the `stop_machine()`. Their task_structs
     were zeroed by the init of their slab neighbours. They are the first to run afterwards, so they
     die first, all at once (2.272589-2.272595 in s61). In s62 a user process (busybox) happened to run
     first.
   - Without cpufreq, WALT never gets past `walt_module_init`. That is why every earlier 6.12 run was fine.
   - The live insmod on a running Android did the same to thousands of tasks while all runqueue
     locks and `tasklist_lock` were held. A silent deadlock instead of an oops fits that (and the
     panic_on_oops/hung_task net did not exist yet).
   - s61 loaded cpufreq before sched-walt and still crashed: the driver's probe deferred until
     `gcc_sc7280` came up (EM lines at 2.263 s by kworker T12, after `insmod sched-walt` at 1.908 s).
     Even with the opposite order, `walt_module_init` checks `topology_update_done` and would run the
     same init. s62 (`sched_energy_aware=0`, `a52.eas=0`) made no difference because EAS is not involved.
   - So the comment in `bsp612/mkramdisk-612.sh:61-62` ("cpufreq-hw must come up before WALT") is
     based on a wrong cause. The load order does not matter.

5. **Other users of the same vendor area.** `soc-repo/drivers/soc/qcom/hung_task_enh.c:54,124,146`,
   `drivers/soc/qcom/mpam/cpu_mpam.c` and `drivers/soc/qcom/minidump_log.c` also use
   `android_task_vendor_data()`. None of them is in a load list today, but each one would corrupt the
   same way without the parameter.

## 2. Driver and DT comparison, 5.4 vs 6.12 (no fault found)

DT node, 5.4 (`downstream-dt/a52sxq-r02.dts`, `cpufreq_hw: qcom,cpufreq-hw`) vs 6.12
(`out-ack/kx/android-r02.dtb`, same label):
- reg 0x18591000/0x18592000/0x18593000 (0x1000 each), reg-names freq-domain0..2: **identical**.
- clocks xo + alternate (GCC GPLL0), `qcom,lut-row-size = <4>`, `qcom,skip-enable-check`,
  interrupts SPI 30/31/19 (`dcvsh0..2_int`), `qcom,sdpm-cx-mx-1/2 = 0x636f08/0x636f0c`,
  `#freq-domain-cells = <2>`: **identical**.
- compatible: 5.4 `qcom,cpufreq-hw-epss`, 6.12 `qcom,cpufreq-epss`. Each matches its own driver's EPSS entry.
- 6.12 adds the children `qcom,limits-dcvs` (isens vref supplies) and `qcom,cpu-voltage-cdev`. 5.4 has
  `qcom,cpu-isolation` children. A separate `qcom,cpufreq-hw-epss-debug@18591000` (domain-top 0x800)
  exists in 6.12.

Register map, 5.4 `cpufreq_qcom_epss_std_offsets`
(`$ANDROID_TREE/kernel/samsung/sm7325/drivers/cpufreq/qcom-cpufreq-hw.c:101-110`) vs 6.12 `epss_soc_data`
(`bsp612/soc-repo/drivers/cpufreq/qcom-cpufreq-hw.c:540-554`):
enable 0x0, domain_state 0x20, freq LUT 0x100, volt LUT 0x200, perf_state 0x320, cycle counter 0x3c4,
intr_clr 0x308, LUT row 4, 40 entries: **identical**. LUT field decode (`LUT_SRC`, `LUT_L_VAL`,
`LUT_CORE_COUNT`, `LUT_VOLT`) is identical. Both write the **LUT index** (not a frequency) to
perf_state (5.4 `:293`, 6.12 `:208`/`:279`). 6.12 adds `reg_dcvs_ctrl = 0xb0` and only **reads** it
(`:787`, per-core DCVS detection). The only init-time access is a read of the enable bit (`:781`).

Real differences:
- **SDPM**: 5.4 writes the new frequency in MHz to the SDPM CX/MX registers before raising and after
  lowering it (`5.4 :286-298, :438-451`). The 6.12 driver ignores `qcom,sdpm-cx-mx-*`. SDPM is the
  power meter that feeds the Policy Engine's peak-current limits (`Documentation/.../thermal/qcom-sdpm.txt`).
  Missing writes give worse peak-current management under heavy load. They do not cause instant
  memory corruption, and the voltage is not set through them. Follow-up only.
- No cpucp/SCMI path: yupik's EPSS is plain MMIO. The driver does not call `qcom_cpucp`/`qcom-dcvs`.
  Those modules are loaded but are not on the cpufreq path.
- LMh: the throttle irqs are requested with `IRQF_NO_AUTOEN` (`:638-639`) and only enabled from the
  notify path. A stale pending dcvsh irq left by the harness would at most schedule `throttle_work`.

## 3. The kexec angle

The 6.18 harness binds the **same** EPSS node with upstream's built-in `qcom-cpufreq-hw`
(`out-ack/.config:723 CONFIG_ARM_QCOM_CPUFREQ_HW=y`, schedutil default). Its dmesg in every run shows
"EM: created perf domain" for cpu0/4/7 at 0.40-0.45 s
(`logs/kx-ab-s62-p2-131451/harness-dmesg.txt`), and it scales frequency for tens of seconds per run
with no corruption. So the hardware, firmware LUT and perf-state writes work on this phone after the
bootloader, and kexec leaves EPSS in a state a second driver can use: 6.12 only reads it at probe. The
only kexec effect that matters here is the one in section 1: **`/chosen/bootargs` from the DT is thrown
away**. That drops this whole Qualcomm set from yupik.dtsi:33:
`rcu_nocbs=0-7 kpti=0 cpufreq.default_governor=performance pcie_ports=compat fw_devlink.strict=1
android_arch_task_struct_size=512 arm64.nosme sysctl.kernel.sched_pelt_multiplier=4 no-steal-acc
swiotlb=0 irqaffinity=0-1 kasan=off sysctl.kernel.panic_on_rcu_stall=1 restrict_cma_redirect=false slub_debug=-`.
A native ABL boot (pack-android-612.sh) should also carry the parameter in the boot image cmdline,
because it is not certain the Samsung ABL keeps DT bootargs.

## 4. Why not undervolt or bad DVFS

- On EPSS the kernel only writes a LUT index. Voltage (CPR/APC) is set by the EPSS firmware. Same
  offsets as 5.4, and the same hardware is driven fine by 6.18 before every run.
- An undervolt gives random faults on one cluster, mostly under load. Here the faults hit the
  stopper threads of all 8 CPUs (silver, gold and prime clusters) within 6 us, with a consistent
  field-level signature (cpu=0, PF_KTHREAD gone, preempt_count underflow). That is a deterministic
  software write.
- The garbled console characters ("creaped", "pagin", "a1sign") also appear **before** the cpufreq
  insmod (seaprobe lines in s60). They are a ramoops/console-transport artefact, not CPU corruption.

## 5. Safe next experiments (in order)

**E1: add the parameter, cpufreq still OFF (verification only).**
Change: append `android_arch_task_struct_size=512` to the 6.12 cmdline: add it to `CMDLINE` in
`drivers612/androidboot/pack-android-612.sh:194-198` so `android-cmdline.txt` carries it, or pass it
in the kx-cycle cmdline string. The current cmdline is about 1041 bytes, so it stays under the 2048 limit.
Check: the "Kernel command line" line shows it, and in `/proc/slabinfo` `task_struct` objsize is
**5696** (5184 + 512), not 5184. Everything else should behave like s59.
What could go wrong: almost nothing. Each task costs 512 bytes more (about 1-2 MB in total). If the
value were rejected (it must be 0-1280), the kernel prints nothing and the size stays 5184. Abort E2 then.

**E2: the parameter + cpufreq, with a fixed frequency.**
Change: E1, plus `A52_CPUFREQ=1` (first stage) and `cpufreq.default_governor=powersave` (fixed at the
lowest LUT entry: the coolest choice, and no frequency changes after the first one). Keep the hang/oops
panic net from helper2.sh.
Check: `/sys/devices/system/cpu/cpufreq/policy{0,4,7}` exist, `scaling_cur_freq` is at the minimum,
there is no WARN/BUG after "EM: created perf domain", `/proc/sys/walt` exists (WALT is up),
and `gcc`/`rpmh-regulator` sync_state completes.
What could go wrong:
- WALT runs for real for the first time on this port. Its hooks (core_ctl CPU halting, walt_lb,
  input boost) are new code paths. A WALT bug would now show up as a scheduler oops. The panic net
  reboots into the harness.
- `walt_init_cycle_counter()` (`walt.c:3532-3545`) waits without a timeout for the cycle-counter
  driver. android-r02.dtb has `/soc/walt/{qcom,cycle-cntr,qcom,epss}`, and s60-s62 got past the
  wait (they reached the `stop_machine`), so this should complete. If it ever does not, the
  walt_init kworker blocks. helper2.sh's `hung_task_panic` then panics the run back into the
  harness, which is safe and easy to recognise.
- Android's post-boot script (ROM `init.kernel.post_boot-yupik.sh:191,203,216`) switches the policies
  to `schedutil` and writes WALT tunables, so the frequency is fixed only until then. Read
  `scaling_governor` and timestamps from the log.
- At powersave the boot is slower, so watchdog timeouts may need more slack.

**E3: real DVFS.**
Change: E2 with `cpufreq.default_governor=performance` (Qualcomm's own boot default), then let
Android's post-boot set schedutil/walt.
What could go wrong: higher temperature at max clocks during boot. The hardware LMh limits and 6.12
tsens (25 thermal zones) are active, but the thermal *cooling* maps have not been checked on 6.12.
Keep the run short and watch the CPU zones. The missing SDPM writes (section 2) only matter for
long, heavy load.

Afterwards:
- Remove the wrong rationale at `bsp612/mkramdisk-612.sh:61-62` and make cpufreq default-on if E2 and E3 pass.
- Consider carrying the whole yupik.dtsi bootargs set into the 6.12 cmdline: at least
  `cpufreq.default_governor=performance` and `rcu_nocbs=0-7`. Check each against the test setup first,
  because `kasan=off` and `slub_debug=-` are no-ops on this build.
- Port the SDPM writes later if long-load stability needs it.
